# Phase 19 Context: Web 管理介面臨床體驗升級與 AI 輔助生成

## 1. 業務背景與臨床痛點
在 Phase 18 交付並實際上線測試後，醫師實機操作反饋出兩大極具價值的核心體驗痛點：
1. **「上傳文件僅有問題清單，缺少答案」**：
   - 診所上傳文件（例如「Endolift - 指示 50」）常為常見問題清單（如 *「4. Endolift與其他非手術治療眼袋有何不同？」*），若直接入庫，答案呈現空白或簡陋標題，醫師無法進行「批准」。
   - **需求**：系統應提供「先生成答案再批准」機制，整合既有的本地 LLM（Qwen3.8-27B），根據問題與診所臨床背景自動生成合規、高品質的繁體中文衛教草稿。
2. **「單筆核准過於繁瑣，需要全選與反選」**：
   - 一份問答集往往有 30~50 題，醫師若在畫面上逐一按 50 次核准，極為耗時且容易操作疲勞。
   - **需求**：提供全選（Select All）、反選（Invert Selection）、批量核准與批量駁回功能，並支援單題內聯微調（Inline Edit）。
3. **「介面視覺體驗美化」**：
   - 升級為現代化醫療科技風格，增加精緻的卡片排版、流暢的微動畫、狀態色彩區隔與浮動批次控制列（Floating Action Bar）。

## 2. 邊界與安全準則（Guardrails）
1. **本地 LLM 與法規防禦保證**：
   - 自動生成答案一律走本地推理（`llama-server`），不外流病患或診所文件至雲端。
   - 生成答案必須強制經過四層法規檢查（正體中文、價格屏蔽、無保證療效、包含就醫評估建議）。
2. **Fail-Closed 審核隔離**：
   - 生成的答案依然為 `review_status='pending'`，經醫師在介面上「批量核准」或「單題核准」後才正式生效。
3. **交易原子性與批次保護**：
   - 批次核准/駁回端點在單一 SQLite 交易內完成，避免部分成功導致狀態不一致。
4. **多 Agent 流水線作業**：
   - 實作端 ➔ Claude 對抗性審查加固（檢查批次大小限制、防 SQL 注入、XSS 轉義）➔ Hermes 終端獨立驗收。
