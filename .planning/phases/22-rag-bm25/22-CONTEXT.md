# Phase 22 Context: RAG 提問檢索優化、BM25 排序與結構化衛教生成

## 1. 業務背景與臨床痛點
在 Phase 20 與 Phase 21 中，系統建立了本機 LLM 衛教生成機制以及 Web 介面的「💬 向 LLM 提問（Phase 20）」檢視功能。然而在醫師實機操作時（以「甲溝炎要怎麼照護？」為例），發現了重大落差：

- **問題現狀與臨床痛點**：
  1. **直接問通用 LLM vs 透過 App 提問的巨大落差**：
     - 直接問本機模型（無限制），模型能條列出詳細的居家照護、溫水浸泡、修剪指甲、何時就醫等完整衛教（但因隨機推薦抗生素藥膏莫匹羅星與口服止痛藥名，違反台灣醫療法規且脫離診所實際處置流程）。
     - 透過 App 提問，模型卻只生硬濃縮了 4 筆門診處置（清創、部分指甲移除縫合、冰敷抬高），完全沒有生活照護與預防細節。
  2. **檢索召回視野狹窄（Recall Bottleneck）**：
     - `src/pageindex/rag_ask.py` 將 FAQ 檢索上限鎖定為 `MAX_FAQ = 4`，每筆截斷 500 字。在知識庫已有 881 筆問答（光甲溝炎就有 123 筆）的情況下，4 筆資料極易被「門診手術」相關條目占滿，導致「居家照護」、「日常修剪預防」等衛教資料被擠出 Context 之外。
  3. **全文檢索缺乏相關度排序（Lack of BM25 Ranking）**：
     - `src/query/search.py` 的 `search_text` 中，FTS5 查詢語句為 `rowid IN (SELECT rowid FROM fts_table WHERE fts_table MATCH ?)`，未指定 `ORDER BY rank`。
     - SQLite FTS5 在沒有 `ORDER BY rank` 時，預設按 rowid 升冪（或 B-Tree 遍歷）回傳，導致較早建立的問答（rowid 較小者，如 ID 2、3、16、17）恆定優先佔據前 4 名，後面高相關度（如 ID 50、59 包含照護與預防）的問答永遠無法進入 Context。
  4. **提問 Prompt 字數與排版過於受限**：
     - 目前 Prompt 限制 `約 100～250 字`，過於簡短，模型無法展開結構化分段說明。

- **核心價值與目標**：
  1. **FTS5 BM25 相關度排序升級**：在 `search_text` 與 `search_faq_cache` 中導入 `ORDER BY rank`，使與查詢語義最貼近的衛教問答優先排在前面。
  2. **檢索 Context 召回擴充**：放寬 `MAX_FAQ` 由 4 筆增加至 8 筆（Qwen 3.8-27B 具備 128k 上下文，8 筆約 3,000 字元，顯存與推論時間完全游刃有餘），大幅提升衛教內容的覆蓋率。
  3. **結構化衛教 Prompt 優化**：調整 `build_ask_prompt`，放寬字數至 250～450 字，明確要求模型按「【門診處置】、【術後／日常照護】、【預防與就醫提醒】」結構化條列輸出。
  4. **法規零妥協**：全域維持 DX-1~6 處方劑量零豁免、無保證療效、深層價格屏蔽（`deep_mask_prices`），確保內容豐富的同時絕不違規。

## 2. 邊界與安全準則（Guardrails）
1. **嚴格接地（Strict Grounding）原則**：
   - 繼續維持「只能根據提供資料回答，不可使用資料外未經證實之處方知識」鐵令。豐富度應來自「檢索出更多、更相關的診所已核准資料」，而非讓 LLM 憑空捏造未授權藥品。
2. **醫療法規合規與處方零豁免**：
   - 輸出的文字必須 100% 通過 `validate_single_faq(..., check_dosage=True)`。
   - 嚴格攔截具體處方指令（DX-4/5）、劑量數字（DX-1/2/3/6）、保證療效詞彙。
3. **效能與推論時間保護**：
   - 上下文擴增至 8 筆 FAQ + 2 棵推理樹，維持在合理 token 規模（約 1,500~2,000 prompt tokens）。
   - 保留 Prompt 前綴「思考過程請保持簡潔（不超過 100 字）」，防止 Qwen 思考過長或輸出超時。
4. **正式資料庫防護**：
   - 本 phase 為查詢與生成層優化，不變更底層 DB schema，正式 `clinic.db` 資料完整性恆定。
