## BLOCKER

### B1. 項目二「候選標記位置」規則與計畫自己的主測資互相矛盾
- 計畫第 3 節規定行內候選標記只能出現在「行首、標點（`。；！\n`）之後、或成對括號」。
- 但計畫的主測資是 `主訴：喉嚨痛 理學檢查：喉嚨紅 診斷：咽喉炎 處置：多喝水`。標記前面是**空白**，不是標點。
- 依規則字面，`理學檢查：` 不是合格候選，測試 1 會維持失敗。
- 相同問題也出現在：
  - `Objective: temp 38 A: flu P: rest`
  - `病人主訴：咳嗽 檢查：無異常`
- 我實測這幾句，現行輸出全部卡在第一段。
- 建議：明訂「空白＋結構化標點（冒號／括號）」也算合格邊界。允許「空白前導」後，必須配套規則避免 `A 35-year-old` 這類誤切（見 B2）。

### B2. 英文「完整單字」標記的規格含糊，Plan 回歸測試可能仍會失敗
- 計畫只把單字母 S/O/A/P 定為強制冒號。
- 多字母詞（Plan／Assessment）寫的是「允許冒號、連字號、**或行首標籤樣式**」。
- 「行首標籤樣式」未定義。若解讀為行首即可，`Plan to evaluate next Monday` 仍會被切成 plan。
- 現況實測：`Plan to observe` → `plan='to observe'`。這正是計畫測試 4 要擋的案例。
- 計畫也沒有說明現有行為的取捨。現行 `S cough\nO clear`（空白分隔）與 `Assessment - flu` 都能正確切分。
- 建議：
  - 全部英文標記（含全稱）一律要求冒號／句點／括號；連字號僅限 ` - `（前後有空白）。
  - 明列「空白分隔的 `S cough` 不再支援」是刻意的行為變更。
  - 確認不影響既有測試與 `/api/v1/soap/records` 的客戶端。

### B3. 否定視窗「前向 1–5 字元」會抹掉真實症狀，反而新增漏報
我用計畫列出的否定詞（`非`、`未見`、`無`、`不見` 等）推演下列常見病歷句，結果會誤抹：

| 句子 | 結果 |
|---|---|
| `非常頭痛` | 「非」在視窗內，頭痛被抹掉 |
| `未見好轉的咳嗽` | 「未見」在視窗內，咳嗽被抹掉 |
| `無法入睡，頭痛` | 視窗規則不明 |
| `無特殊不適，咳嗽三天` | 靠逗號斷開才倖免 |

反方向還有漏攔：

- `無發燒、咳嗽、腹瀉`：計畫規定 `、` 終止否定範圍，所以咳嗽、腹瀉仍會被當成現存症狀。
- 同一個列舉句，`、` 既要作為「無發燒、無咳嗽」的分界，又不能截斷列舉，計畫沒有處理。
- `感冒，無流感`、`沒有發燒`：「沒有」寫在詞表，但視窗與詞表順序未規範。
- `不是頭痛，是頭暈`：「不是」不在詞表。

現況（未修）的偽陽性我也重現了：`沒有發燒` → `['發燒']`、`感冒，無流感` → 兩者都命中。

建議：
- 否定詞改為精確片語白名單，而非單字。例如排除「非常」「無法」「未見好轉」。
- 規範列舉延續規則：`無A、B` 視為 A、B 皆被否定。
- 補齊「但／然而／不過」作為否定範圍的終止詞。
- 加入反向測試：`非常頭痛`、`未見好轉的咳嗽`、`無發燒、咳嗽`、`無發燒，但有咳嗽`。

### B4. 計畫擅自決定了「疑似／R/O」的醫療語意，又把它列為「待決策」
- 計畫第 3 節把 `r/o`、`rule out` 放進否定詞表，測試 3（`test_insights_english_rule_out`）也斷言 R/O 流感必須排除。這等於已採用方案 A。
- 但「需要使用者決策」的第 1 點又說「疑似／R/O」要等使用者選 A 或 B。
- 現況實測：`疑似普通感冒` 目前會被收進 conditions。
- 兩處衝突：
  - 方案 A 若採行，`疑似` 必須進詞表，計畫的詞表漏了它。
  - 測試與實作不得在使用者回覆前就動工。
- 建議：
  - 把 `r/o`、`疑似`、`鑑別診斷` 整組從否定詞表移出，歸入「待使用者決策」。
  - 實作排在決策之後。測試 3 暫標 `xfail` 或延後。

### B5. 「診斷以 Assessment 為準，空白時降級讀 subjective」會重新引入計畫想解決的汙染
- 計畫測試 6（同事得流感）只涵蓋「Assessment 有值」的情況。
- 如果 assessment 為空，改讀 subjective，`自述同事罹患流感` 仍會被當成病患診斷。
- 我實測 `{'subjective':'同事得流感','assessment':'感冒'}` 目前確實回傳 `['感冒','流感']`，所以問題是真的。
- 但降級條件的設計只解了一半。
- 建議：
  - assessment 為空就不產生 `conditions`，只保留 `symptoms`。
  - 或者降級時要求主詞為病患，這有誤判風險，需經使用者決策。
  - 另外 `/api/v1/soap/records` 路由有「僅帶 raw_text、無標記」的情境，此時 assessment 一定是空的，conditions 全數消失。這對退化路徑的影響需要寫進計畫。

## WARNING

### W1. 項目一測試寫法有污染正式庫的風險
- 測試 2 是 `main([])`，預設 `--db` 指向正式 clinic.db，且**不帶 `--dry-run`**。
- 一旦實作回歸，或在 TDD 紅燈階段誤改條件，這個測試會真的對正式庫執行 `apply_soap_schema`。
- 測試 1、3 也硬依賴 `clinic.db`。該檔案已 gitignore，CI 或新環境不存在時會直接失敗。
- 建議：
  - 以 `monkeypatch.setattr(mod, "PROD_DB_PATH", tmp_path/"clinic.db")` 將「正式庫」改指向暫存複本。
  - 所有 `main([...])` 呼叫都要在此保護下執行。
  - 另補一個測試：以 `sqlite3.connect` 的 mock 斷言 dry-run 完全沒有連線。
- 目前專案沒有 `scripts/__init__.py`。`tests/conftest.py:62` 的 `from scripts.migrate_soap_schema import ...` 靠 namespace package 運作。計畫的測試 import 路徑沿用即可，但要在計畫中說明。

### W2. 項目一的驗收指令含一個無害但冗餘的前置檢查
- dry-run 在 `target_path.exists()` 檢查後才進入。若 `--db` 不存在，仍回 2，這是合理行為（不要自動建檔）。
- 但計畫「預期輸出」未說明這個分支。
- 另外 dry-run 的修法並未改變第 3 步讀取 DDL 的位置，因此預覽仍然完全唯讀。我用 `--db <空檔>` 實測：
  - 輸出含 `CREATE TABLE IF NOT EXISTS soap_records` 與 `tokenize='trigram'`。
  - 該檔案不變。
- 這個修法本身正確、風險低。建議把這一步與 sha256 驗證寫進同一個驗收指令。

### W3. 項目三需要改動路由，但計畫宣稱不越界
- 計畫要求 symptoms 取自 subjective＋objective。
- 但 `src/api/routes/soap.py` 呼叫 `extract_general_medical_insights` 時（第 118 行附近），傳入的字典只有 `subjective`、`objective`、`assessment`、`plan`，這部分已經帶入 objective。我確認 route 實際有傳 objective，所以不必改路由，此項降為警示。
- 然而同一路由在合併標籤時會把 `suggested_tags` 全數寫進 `soap_records.tags`，所以誤判的標籤會直接汙染醫師檢索。
- 建議在計畫中補一項「路由層無需改動」的聲明，並加一個端到端測試：POST 含否定句的 SOAP，驗證存入的 tags。

### W4. 英文縮寫詞庫會產生子字串誤判，計畫沒有規範比對方式
- 計畫要加入 `URI`、`AGE`、`GERD`，並把 `no` 列為英文否定詞。
- 若用 `in` 子字串比對且不分大小寫：
  - `uri` 會命中 `during`。
  - `age` 會命中 `35-year-old age`、`damage`。
  - `no` 會命中 `nose`、`normal`、`know`。
- 建議：英文一律用 `\b` 單字邊界。縮寫要求原文大寫比對，或限定出現在 assessment 區段。
- 計畫測試 3 預期「命中急性扁桃腺炎」，但詞表只有 `扁桃腺炎`，沒有 `急性扁桃腺炎`。需先決定 `Acute tonsillitis` 對照到哪個標準詞。
- 另外 `URI → 感冒`、`AGE → 急性腸胃炎` 是臨床對照，計畫把它當工程細節。URI 不等同感冒，這個對照應納入使用者決策（第 2 點已問「數量」，沒問「對照是否正確」）。

### W5. 否定上下文偏窄，TDD 的「先紅」不成立的測試
計畫要求先寫失敗測試，但以下計畫測試在現況就會通過，無法驗證修改前後差異：

- 項目二測試 5（`病患主訴未做過任何身體檢查與評估`）：我實測現況整句留在 subjective，已經通過。
- 項目二測試 7（純逐字稿 fallback）：現況已通過。
- 項目三測試 3、4：現況因詞表沒有英文與「陰性」，`conditions` 本來就是 `[]`，斷言「不含流感」現況就通過。

這些是「防回歸」測試，應標註為綠燈守門，不能算紅燈證據。
同時應補真正的紅燈測試：先在現況實測確認會失敗。

### W6. 內嵌切分可能碎裂既有的合法文字
計畫第 3 節的內嵌切分雖有「必須帶冒號」，但仍有下列風險，計畫的測試沒有涵蓋：

- 病歷慣用的「檢查：」出現在主訴敘述中，例如 `病人主訴：咳嗽 檢查：無異常` 會被切到 objective。這是正確的，但若「處置」類詞出現在病史描述，例如 `過去處置：…`，會被誤切。
- 既有測試的 plan 內有 `衛教事項：` 在句中（`開立退燒藥。衛教事項：…`）。新規則下「。」後的標記會成為候選，雖然仍屬 plan，但 subjective 內若有 `。診斷：`、`。處置：` 的敘述性文字也會被切開。
- 建議補反例測試：標記詞出現在敘事句中間且帶冒號、以及連續重複標記（`主訴：…主訴：…`）的合併行為。
